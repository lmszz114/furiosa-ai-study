## A. NPU LLM 추론 성능

NPU에 띄운 LLM(`furiosa-llm serve`, OpenAI 호환 API)을 LangChain `ChatOpenAI`로 불러, **얼마나 빠른지**를 여러 각도에서 측정하고 최적화한다. 생성 호출은 공통 모듈(`kingkeras.py`)로 빼두고 가져다 쓴다.

```python
# kingkeras.py — LLM 생성을 모듈로 분리
from langchain_openai import ChatOpenAI
def get_llm(max_tokens=None, temperature=None, top_p=None):
    return ChatOpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY",
                      max_tokens=max_tokens, temperature=temperature, top_p=top_p)
```

### A-1. 성능 측정 지표

LLM 추론 속도는 하나의 숫자가 아니라 **여러 지표**로 본다.

- **Latency(지연시간)**: 요청부터 응답 완료까지의 **총 시간**. 한 번은 들쭉날쭉하니 여러 번 재서 평균 낸다.
- **TTFC(Time To First Chunk)**: 요청 후 **첫 응답 조각이 나오기까지** 걸린 시간 = 사용자가 "반응이 시작됐다"고 체감하는 속도. 스트리밍에서 중요하며, `next(iter(llm.stream(prompt)))`로 첫 조각 하나만 꺼내 간결하게 잰다.
- **TPS(Tokens Per Second)**: 초당 생성 **토큰** 수 = 생성 처리량. `usage_metadata["output_tokens"] ÷ 시간`으로 정확히 계산한다.
- **usage_metadata**: 응답 객체에 담긴 **실제 입력·출력 토큰 수**(`response.usage_metadata`). `max_tokens`(설정 상한)가 아닌 실제 토큰이라 TPS 계산이 정확해진다.

```python
response = llm.invoke(prompt)
tokens = response.usage_metadata["output_tokens"]   # 실제 생성 토큰
tps = tokens / elapsed
```

- **Prefill / Decode (추론 2단계)**: LLM 추론은 **입력 프롬프트를 한 번에 처리하는 Prefill**(병렬이라 빠름)과 **출력 토큰을 하나씩 순서대로 생성하는 Decode**(토큰 수만큼 반복이라 느림)로 나뉜다. 그래서 **출력이 길수록(decode가 많을수록) 응답시간이 크게 는다.**

### A-2. 추론 최적화 — 배칭과 캐시

- **연속 배칭(Continuous Batching)**: 여러 요청을 동시에 받아 NPU가 **묶어서** 처리하는 기법. NPU는 병렬 연산에 강해, 하나씩 처리하는 것보다 묶으면 전체 처리량(TPS)이 오른다. `ThreadPoolExecutor`로 동시 요청 수(1·2·4·8)를 늘려가며 관찰한다. 요청마다 인자가 다르면 `pool.submit(함수, 인자)`로 맡기고 `future.result()`로 받는다(같은 함수를 리스트에 일괄 적용하는 `pool.map`과 구분).
- **KV 캐시(Key-Value Cache)**: 토큰을 하나씩 생성할 때 **앞서 계산한 토큰들의 Key·Value를 저장해 재사용**하는 장치. 없으면 새 토큰마다 전체를 다시 계산해야 해 느리다. 입력·출력이 길수록 저장할 게 많아져 **사용량(메모리)이 는다.**
- **프리픽스 캐시(Prefix Cache)**: 여러 요청이 **같은 앞부분(접두사)** 을 공유하면 그 부분 계산을 재사용한다. 같은 긴 접두사에 질문만 바꿔 반복하면 **적중률(hit rate)** 이 오르고 빨라진다. 누적 수치라, 요청 직전·직후를 각각 재서 빼면(`before`/`after`) 이번 요청의 적중률만 뽑을 수 있다.

### A-3. 요청 방식 비교와 처리량 지표

```python
# 순차: for문 — 앞 요청이 끝나야 다음 (느림)
for prompt in prompts: llm.invoke(prompt)
# 동시: ThreadPoolExecutor — 한꺼번에 (배칭되어 빠름)
with ThreadPoolExecutor(max_workers=4) as ex:
    results = list(ex.map(ask, prompts))
```

- **단일 < 순차 < 동시**: 같은 요청 수라도 동시 처리가 전체 시간이 짧고 처리량이 높다.
- **TPS vs RPS**: 둘 다 처리량이지만 단위가 다르다. **TPS**(초당 토큰) = "얼마나 빨리 글자를 뽑나", **RPS(Requests Per Second)**(초당 요청) = "얼마나 많은 사용자를 받나". 서비스 운영엔 RPS, 생성 속도엔 TPS가 중요하다.
- **트레이드오프**: 동시 요청 수를 늘리면 **전체 처리량(RPS·TPS)↑** 이지만 **개별 요청의 평균 지연도 다소 ↑**(자원을 나눠 쓰므로). "많이 받기 vs 하나를 빨리"의 균형점을 동시 요청 수로 조절한다.
- **서버 메트릭**: 클라이언트 측정과 별개로, 서버 `/metrics` 주소를 `requests.get`으로 읽어 **서버가 지금 얼마나 바쁜지**를 직접 본다(`num_requests_running`/`waiting` = 혼잡도, `kv_cache_usage_percent`, `e2e_request_latency_seconds`).

### A-4. 스케줄링 — Overlap vs Eager

NPU 서빙 엔진이 요청을 처리하는 **스케줄링 방식** 두 가지.

- **Overlap Scheduling**: NPU가 **현재 배치를 처리하는 동안** CPU가 **다음 배치를 미리 준비**하도록 겹쳐 실행하는 최적화. `--enable-overlap-scheduling`으로 켠다.
- **Eager Scheduling**: 겹치지 않고 **순차 처리**하는 기본(default) 방식.
- 실측상 두 방식의 차이는 **미미**했고, 어떤 게 유리한지는 **워크로드(요청 패턴·동시성)에 따라 다르다**(Overlap이 늘 빠른 건 아님).

**NPU 성능 지표 한눈 정리**

| 지표 | 뜻 | 단위 | 측정 위치 |
|---|---|---|---|
| Latency | 요청~완료 총 시간 | 초 | 클라이언트 |
| TTFC | 첫 조각까지 시간(체감 속도) | 초 | 클라이언트(stream) |
| TPS | 초당 출력 토큰 | tokens/s | 출력토큰÷시간 |
| RPS | 초당 처리 요청 | req/s | 요청수÷시간 |
| KV/프리픽스 캐시 | 재사용률·메모리 | % | 서버 /metrics |
| running/waiting | 처리중/대기중 요청 | 개 | 서버 /metrics |

## B. 머신러닝 하이퍼파라미터 튜닝 마무리 — HalvingGridSearchCV

앞서 배운 **GridSearchCV**(모든 조합 전부)·**RandomizedSearchCV**(무작위 일부)에 이어, 세 번째 방식 **HalvingGridSearchCV**로 튜닝 3종을 완성했다.

```python
from sklearn.experimental import enable_halving_search_cv  # 실험적 기능 활성화(먼저 import)
from sklearn.model_selection import HalvingGridSearchCV

model = HalvingGridSearchCV(xgb, parameters, cv=kfold, refit=True,
                    min_resources=50, max_resources=1000, factor=2, verbose=1)
```

- **작동 방식(연속 절반 탈락, successive halving)**: 1라운드에 **적은 자원(데이터)** 으로 **많은 후보를 전부** 평가 → 하위 절반 탈락 → 다음 라운드는 **자원을 `factor`배 늘리고** 살아남은 후보만 평가 → 반복. 토너먼트처럼 유망한 후보에 자원을 점점 몰아준다.
- **핵심 아이디어**: 처음부터 모든 후보에 전체 데이터를 쓰면 느리다. **적은 데이터로 가망 없는 후보를 빨리 걸러내고** 유망 후보에만 자원을 집중해 빠르게 좋은 조합을 찾는다.
- **파라미터**: `min_resources`(첫 라운드 자원 시작값)·`max_resources`(최대 자원)·`factor`(라운드마다 자원 ×factor, 후보 ÷factor).

| 방식 | 전략 | 속도 |
|---|---|---|
| GridSearchCV | 모든 조합 × 전체 데이터 | 느림 |
| RandomizedSearchCV | 무작위 일부 조합 | 빠름 |
| HalvingGridSearchCV | 적은 자원→유망 후보에 자원 집중(절반씩 탈락) | 빠름(체계적) |

## C. 딥러닝 기초

### C-1. 활성화 함수 8종

**활성화 함수**는 뉴런 출력을 결정하는 함수로, 가장 중요한 역할은 **비선형성**을 주는 것이다. 없으면 층을 아무리 쌓아도 하나의 선형식과 같아져 복잡한 패턴을 못 배운다. 8개를 numpy로 직접 구현해 그래프로 비교했다.

| 함수 | 출력 범위 | 특징 | 음수 처리 |
|---|---|---|---|
| **Sigmoid** `1/(1+e^-x)` | 0~1 | 확률 출력, 이진분류 출력층 | 기울기 소실 |
| **Tanh** | −1~1 | 0 중심, Sigmoid 개선 | 기울기 소실 |
| **ReLU** `max(0,x)` | 0~∞ | 가장 많이 씀, 간단·빠름 | 0으로 죽임(Dying ReLU) |
| **SiLU(Swish)** `x·sigmoid(x)` | 약 −0.3~∞ | 부드러운 ReLU, 성능↑ | 부드럽게 통과 |
| **Mish** | 약 −0.3~∞ | 부드러움, 성능↑ | 부드럽게 통과 |
| **ELU** | −α~∞ | 음수 지수곡선, 0중심 근접 | 지수 곡선 통과 |
| **SELU** | 스케일된 ELU | 자기 정규화(고정 상수) | 지수 곡선 통과 |
| **Leaky ReLU** `x>0:x, x≤0:αx` | −∞~∞ | Dying ReLU 해결 | 작은 기울기(αx)로 통과 |

- **큰 흐름**: Sigmoid·Tanh(기울기 소실) → **ReLU**(기본, 간단하지만 Dying) → 이를 고친 변형들(Leaky ReLU·ELU·SELU)과 더 부드러운 SiLU·Mish. 실무는 ReLU를 기본으로 쓰고 성능이 필요하면 SiLU/Mish 등을 시도한다.

### C-2. Softmax — 다중 분류 출력층

```python
softmax = lambda x : np.exp(x) / np.sum(np.exp(x))
```
- 여러 출력값을 각각 `exp()`로 키운 뒤 **전체 합으로 나눠**, **합이 1인 확률 분포**로 바꾼다 → "각 클래스일 확률". **Sigmoid**가 이진 분류(확률 하나)라면 **Softmax**는 **다중 분류**(여러 클래스 확률)이고, 다중분류 모델의 마지막 층은 `Dense(클래스수, activation='softmax')`다.

### C-3. 경사하강법 · 학습률 — 신경망 학습의 원리

손실(loss)을 가장 작게 만드는 지점을 찾는 방법이 **경사하강법(Gradient Descent)** 이다.

```python
f = lambda x : x**2 - 4*x + 6      # 손실 함수(아래로 볼록, 최소점 x=2)
gradient = lambda x : 2*x - 4      # f를 미분한 기울기
x = -10.0; learning_rate = 0.1
for i in range(50):
    x = x - learning_rate * gradient(x)   # ★ 기울기 반대 방향으로 조금씩 이동
```

- **핵심 공식 `x = x - lr * gradient(x)`**: 기울기(미분)의 **반대 방향(내리막)** 으로 조금씩 이동하면, 어디서 시작하든 **골짜기 바닥(최소점)으로 수렴**한다. **신경망은 이 방식으로 가중치를 고쳐 손실을 줄인다** — 모델의 "학습"이 바로 이 과정이다.
- **학습률(Learning Rate)**: 한 번에 이동할 **보폭**(공식의 `lr`). **너무 크면** 최소점을 건너뛰며 발산하고, **너무 작으면** 학습이 느리다. 적절한 학습률 선택이 학습의 핵심이다.

### C-4. TensorBoard — 학습 과정 시각화

```python
from tensorflow.keras.callbacks import TensorBoard
tb = TensorBoard(log_dir='.../_keras80/', write_graph=True, write_images=True)
model.fit(x, y, ..., callbacks=[es, tb])
```
- 학습 로그(loss·acc 등)를 폴더에 기록하는 **콜백**. `model.fit`의 `callbacks`에 넣으면 에폭마다 기록이 쌓이고, 터미널에서 `tensorboard --logdir=경로`를 실행해 브라우저(보통 localhost:6006)에서 **학습 곡선을 그래프로** 본다. `print`로 숫자만 보는 것보다 과적합·학습 정체를 한눈에 파악할 수 있다.

## D. 파이썬 문법 — map / lambda

데이터를 간결하게 처리하는 두 문법.

- **`map(함수, 반복가능객체)`**: 각 원소에 함수를 한 번씩 적용. 결과는 바로 리스트가 아니라 지연 평가되는 map 객체라 **`list()`로 감싸야** 값이 나온다.
- **`lambda 인자 : 식`**: 이름 없이 한 줄로 만드는 **익명 함수**. `aaa = lambda x: x*2`는 `def aaa(x): return x*2`와 같다.
- **`map`+`lambda`+조건식**: `list(map(lambda x: "합격" if x>=60 else "불합격", score))`처럼 묶어 데이터 변환을 간결하게 쓴다.

## 한 주 핵심 한 줄

> **NPU 추론 성능**은 Latency·TTFC·TPS·RPS·usage_metadata로 여러 각도에서 재고, 추론이 Prefill(입력 일괄)·Decode(출력 하나씩) 2단계임을 이해한 뒤, **연속 배칭·KV/프리픽스 캐시·Overlap 스케줄링**으로 처리량을 높인다(동시성↑ 시 처리량↑·개별지연↑ 트레이드오프, 서버 `/metrics`로 혼잡도 확인). **튜닝**은 HalvingGridSearchCV(적은 자원→유망 후보 집중)로 Grid·Random에 이어 3종을 완성했다. **딥러닝 기초**는 활성화 함수 8종(비선형성, ReLU 기본·변형들)과 Softmax(다중분류 출력) → **경사하강법**(`x = x - lr·gradient`로 손실 최소점 찾기 = 학습 원리)·학습률(보폭) → TensorBoard(학습 곡선 시각화)로 "신경망이 어떻게 학습하는가"를 짚었다. 파이썬 `map`·`lambda`로 간결한 데이터 변환도 익혔다.
