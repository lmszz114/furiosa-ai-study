## 1. f21_3 — 연속 배칭 심화 (시차 요청, submit)

어제 배운 연속 배칭을, **요청마다 출발 시각·길이를 다르게** 해서 더 현실적으로 관찰한다. 요청이 서로 다른 시점에 들어와도 NPU가 진행 중인 배치에 끼워 처리하는 모습을 본다.

```python
from concurrent.futures import ThreadPoolExecutor
from kingkeras import run_once

def ask(name, delay, max_tokens):
    time.sleep(delay)                     # 요청마다 다른 시점에 출발
    print(f"{name} 요청 시작", flush=True)
    result = run_once(f"...요청 {name}", max_tokens)
    print(f"{name} 요청 완료", flush=True)
    return result

with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [
        pool.submit(ask, "A", 0, 800),    # 0초에 출발, 긴 출력
        pool.submit(ask, "B", 1, 200),    # 1초 뒤 출발
        pool.submit(ask, "C", 2, 1000),
        pool.submit(ask, "D", 3, 200),
        pool.submit(ask, "E", 4, 300),
    ]
    results = [f.result() for f in futures]   # 각 결과 받기
```

- **`pool.submit(함수, 인자들)`**: 작업 하나를 스레드풀에 **맡기고 `Future`(미래 결과표)를 바로 돌려받는다.** 나중에 `future.result()`로 그 결과를 꺼낸다. (어제 쓴 `pool.map`은 "같은 함수를 리스트에 일괄" 적용이고, `submit`은 **요청마다 다른 인자**를 줄 때 쓴다.)
- **`time.sleep(delay)`** 로 A~E가 0·1·2·3·4초에 **시차를 두고 출발**한다. 먼저 들어온 요청이 처리되는 중에 뒤 요청이 도착해도, 연속 배칭이 **진행 중인 배치에 합류**시켜 함께 처리하는 흐름을 관찰한다.

## 2. f22 — KV 캐시 (복습)

어제 다룬 내용. 입력/출력 길이를 다르게 해 **KV 캐시 사용률**을 본다(`run_once`로 토큰·시간 측정, `input()`으로 멈춰 서버 상태 확인). KV 캐시는 앞서 계산한 토큰의 Key·Value를 저장해 재사용하는 장치로, 입력·출력이 길수록 사용량이 는다.

## 3. f23 — 프리픽스 캐시 적중률

**프리픽스 캐시(Prefix Cache)** 는 여러 요청이 **같은 앞부분(접두사)** 을 공유할 때 그 부분 계산을 재사용하는 최적화다. 긴 공통 접두사(`prefix`)에 질문만 바꿔 반복 요청하며 **적중률이 오르는지** 본다.

```python
# f23_prefix_cache1 — 같은 prefix + 다른 질문 반복
prefix = "NPU 추론 최적화에 대한 설명입니다." * 150    # 긴 공통 접두사
for i in range(1, 5):
    prompt = prefix + f"\n질문 {i}: KV Cache란?"       # 앞부분은 같고 질문만 다름
    result = run_once(prompt, 100)
    print("응답 시간:", round(result["elapsed"], 3), "입력 토큰:", result["input_tokens"])
    get_cache_metrics()                                 # 누적 적중률 확인
```

```python
# f23_prefix_cache2 — '이번 요청'의 적중률만 따로 계산
for i in range(1, 5):
    before = get_cache_metrics()      # 요청 전 누적 수치
    result = run_once(prompt, 100)
    after = get_cache_metrics()       # 요청 후 누적 수치
    hits = after["hits"] - before["hits"]          # 이번에 늘어난 적중 수
    queries = after["queries"] - before["queries"] # 이번에 늘어난 조회 수
    hit_rate = hits / queries * 100 if queries > 0 else 0
    print("이번 적중률:", round(hit_rate, 2), "%")
```

- 같은 긴 접두사를 반복 요청하면, 두 번째 요청부터 **그 접두사 부분이 캐시에 있어 재계산을 건너뛴다** → 적중률이 오르고 응답이 빨라진다.
- **`before`/`after` 차이로 "이번 요청"만 계산**(`f23_2`): `get_cache_metrics()`가 돌려주는 값은 서버 시작 이후 **누적**이라, 요청 직전·직후를 각각 재서 빼면 **이번 한 번의 적중률**을 알 수 있다. (누적값만 보면 개별 요청 효과가 안 보이므로 차이를 쓴다.)

## 4. f24~f26 — 단일 / 순차 / 동시 요청

요청을 처리하는 세 가지 방식의 처리량을 비교한다.

```python
# f24_single — 요청 1개
resp = llm.invoke("NPU의 장점 3가지를 설명해줘.")   # 단일 요청의 지연·토큰 측정
```
```python
# f25_sequential — 8개를 하나씩 순서대로
start = time.perf_counter()
for prompt in prompts:        # ★ for문: 앞 요청이 끝나야 다음
    llm.invoke(prompt)
elapsed = time.perf_counter() - start
print("요청 처리량:", round(len(prompts) / elapsed, 3), "req/s")
```
```python
# f26_concurrent — 8개를 동시에
with ThreadPoolExecutor(max_workers=4) as executor:
    results = list(executor.map(ask, prompts))   # ★ 동시 처리
print("요청 처리량:", round(len(prompts) / elapsed, 3), "req/s")
```

- **단일(f24)**: 요청 하나의 지연·토큰을 본다(기준점).
- **순차(f25)**: `for`문으로 **하나씩** 처리 — 앞 요청이 끝나야 다음이 시작된다. 느리다.
- **동시(f26)**: `ThreadPoolExecutor`로 **여러 개를 한꺼번에** 보낸다. NPU가 배칭해 처리하므로 **같은 8개라도 전체 시간이 짧고 처리량(req/s)이 높다.**
- **`req/s`(초당 요청 수)** = 요청 개수 ÷ 전체 시간. 순차보다 동시가 이 값이 크게 나온다.

## 5. f27 — RPS (초당 요청 수)

**RPS(Requests Per Second)** 는 초당 처리하는 **요청 수**다. 토큰 처리량(TPS)과 함께 서버 성능을 나타내는 핵심 지표다. 16개 요청을 동시에 보내 둘 다 측정한다.

```python
def ask(prompt):
    response = llm.invoke(prompt)
    usage = response.usage_metadata or {}
    return usage.get("output_tokens", 0)      # 각 요청의 출력 토큰 수

with ThreadPoolExecutor(max_workers=4) as executor:
    tokens = list(executor.map(ask, prompts))   # 16개 동시
total_tokens = sum(tokens)

print("Output TPS:", round(total_tokens / elapsed, 2))   # 초당 출력 토큰
print("RPS:", round(len(prompts) / elapsed, 2))          # 초당 요청 수
```

- **TPS vs RPS**: 둘 다 처리량이지만 **단위가 다르다.**
  - **TPS**(Tokens/s): 초당 생성한 **토큰** 수 → "얼마나 빨리 글자를 뽑나".
  - **RPS**(Requests/s): 초당 처리한 **요청** 수 → "얼마나 많은 사용자를 받나".
- 서비스 운영 관점에선 RPS(동시 사용자 처리량)가, 생성 속도 관점에선 TPS가 중요하다.

## 6. f28 — 동시 요청 수별 종합 비교

동시 요청 수(`workers`)를 1·2·4·8로 바꿔가며 **전체 시간·평균 지연·RPS·TPS를 한 번에** 비교한다.

```python
def ask(prompt):
    start = time.perf_counter()
    response = llm.invoke(prompt)
    elapsed = time.perf_counter() - start
    tokens = (response.usage_metadata or {}).get("output_tokens", 0)
    return elapsed, tokens                     # 지연·토큰 둘 다 반환

for workers in [1, 2, 4, 8]:
    with ThreadPoolExecutor(max_workers=workers) as executor:
        results = list(executor.map(ask, prompts))
    latencies = [r[0] for r in results]
    total_tokens = sum(r[1] for r in results)
    print(f"Workers: {workers}")
    print("평균 지연:", round(statistics.mean(latencies), 2), "초")
    print("요청 처리량:", round(len(results) / total_time, 2), "req/s")
    print("Output TPS:", round(total_tokens / total_time, 2))
```

- **관찰되는 경향(트레이드오프)**: 동시 요청 수를 늘리면
  - **전체 시간 ↓, RPS·TPS ↑** (처리량 증가) — 배칭 효과
  - 단, **개별 요청의 평균 지연은 다소 ↑** (자원을 나눠 쓰니 요청 하나하나는 조금 느려질 수 있음)
- 즉 "**처리량(많이 받기) vs 개별 지연(하나를 빨리)**"의 균형점을 동시 요청 수로 조절한다. `statistics.mean`으로 평균 지연을 구한다.

## 7. f29 — 서버 메트릭 직접 조회

NPU 서버의 `/metrics` 주소에서 **서버 내부 상태**를 직접 읽는다. 클라이언트에서 재는 시간과 달리, **서버가 지금 얼마나 바쁜지**를 보여준다.

```python
import requests
url = "http://127.0.0.1:8000/metrics"
response = requests.get(url, timeout=5)
response.raise_for_status()                    # 요청 실패 시 에러 발생

keywords = [
    "num_requests_running",       # 지금 처리 중인 요청 수
    "num_requests_waiting",       # 대기 중인 요청 수
    "kv_cache_usage_percent",     # KV 캐시 사용률
    "e2e_request_latency_seconds" # 요청 전체(end-to-end) 지연
]
for line in response.text.splitlines():
    if line.startswith("#"):
        continue
    if any(word in line for word in keywords):   # 관심 지표만 출력
        print(line)
```

- **`requests.get(url)`**: 어제 `urllib`로 하던 걸 더 간결한 `requests` 라이브러리로 한다. **`raise_for_status()`** 는 응답이 실패(4xx·5xx)면 바로 에러를 내 문제를 빨리 알게 한다.
- **서버 지표 뜻**:
  - `num_requests_running` / `num_requests_waiting`: 지금 **처리 중 / 대기 중**인 요청 수 → 서버 혼잡도.
  - `kv_cache_usage_percent`: KV 캐시가 얼마나 찼는지(메모리 여유).
  - `e2e_request_latency_seconds`: 요청이 서버에 들어와 나가기까지의 전체 지연.
- **`any(word in line for word in keywords)`**: 그 줄에 관심 키워드 중 **하나라도 들어있으면** 출력(수많은 지표 중 필요한 것만 거르기).

## 8. 성능 지표 총정리

| 지표 | 뜻 | 단위 | 어디서 |
|---|---|---|---|
| **Latency(지연)** | 요청 하나 완료까지 시간 | 초 | 클라이언트 측정 |
| **TPS** | 초당 생성 출력 토큰 수 | tokens/s | 출력토큰 ÷ 시간 |
| **RPS** | 초당 처리 요청 수 | req/s | 요청수 ÷ 시간 |
| **KV 캐시 사용률** | 캐시(메모리)가 찬 정도 | % | 서버 /metrics |
| **프리픽스 캐시 적중률** | 공통 접두사 재사용 비율 | % | 서버 /metrics |
| **running/waiting** | 처리 중/대기 중 요청 수 | 개 | 서버 /metrics |

- **요청 방식**: 순차(for, 하나씩) < 동시(ThreadPool, 배칭) — 동시가 처리량(RPS·TPS) 높음. 단 동시성↑ 시 개별 지연은 다소 늘 수 있음.
- **캐시**: KV 캐시(한 요청 내 토큰 재사용) + 프리픽스 캐시(요청 간 공통 접두사 재사용)가 속도를 높인다.
- **측정 위치**: 클라이언트(내 코드의 시간·토큰) + 서버(/metrics의 혼잡도·캐시) 양쪽을 본다.

## 한 줄 요약

> NPU 추론 성능은 **요청 방식·캐시·서버 상태** 세 축으로 측정한다. **요청 방식**: 순차(`for`, 하나씩)보다 동시(`ThreadPoolExecutor`, 연속 배칭)가 처리량이 높고, 요청마다 다른 인자는 `pool.submit`+`future.result()`로 보낸다. 처리량은 **TPS**(초당 토큰)와 **RPS**(초당 요청)로 나눠 보며, 동시 요청 수를 늘리면 처리량↑·개별 지연↑의 트레이드오프가 있다. **캐시**: KV 캐시(한 요청 내 재사용)와 프리픽스 캐시(요청 간 공통 접두사 재사용, `before/after` 차이로 이번 적중률 계산)가 속도를 높인다. **서버 상태**: `/metrics`를 `requests`로 읽어 `num_requests_running/waiting`·`kv_cache_usage`·`e2e_latency`로 서버 혼잡도를 직접 확인한다.
