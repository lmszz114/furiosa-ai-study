## A. 합성곱으로 시계열 다루기

### A-1. 시계열을 CNN(Conv2D)으로 — 이미지로 보기

시계열 데이터 jena는 원래 `(N, 144, 13)` = (샘플, 144 타임스텝, 13 피처)의 3차원이다. 이것을 **1채널 이미지**로 간주하면 Conv2D로 처리할 수 있다. 데이터 전처리(split_x·x/y 분리·스케일링)는 RNN 때와 같고 모델 부분만 바뀐다.

```python
from tensorflow.keras.layers import Reshape, Conv2D, MaxPooling2D, Flatten

model = Sequential()
model.add(Reshape(target_shape=(144, 13, 1), input_shape=(144, 13)))  # 3D → 4D(이미지)
model.add(Conv2D(64, (2,2), activation='relu'))
model.add(MaxPooling2D())
model.add(Conv2D(32, (2,2), activation='relu'))
model.add(MaxPooling2D())
model.add(Flatten())
model.add(Dense(256, activation='relu'))
model.add(Dense(1))
```

- **모델 안에서 Reshape한다.** 데이터를 `(N,144,13)` 그대로 두고 첫 층 `Reshape`로 `(144,13,1)` 4차원(높이·너비·채널)으로 바꿔 Conv2D에 넣는다.
- **`target_shape`에 `-1`을 넣지 않는다.** `(-1,144,13,1)`처럼 쓰면 차원이 하나 더 생겨 5D가 되어 에러다. 배치 차원은 Reshape 대상이 아니므로 `(144,13,1)`만 적는다.
- **Conv2D는 메모리를 많이 쓴다.** 중간 특성맵이 커서 `batch_size`가 크면 OOM(`ResourceExhaustedError`)이 난다. batch를 작게(예: 256) 쓰고, `MaxPooling2D`로 특성맵을 절반씩 줄여 메모리·연산을 아낀다.

**CNN vs LSTM 결과(실측).** 같은 jena에서 LSTM은 R² 0.9987·약 3347초, CNN(Conv2D)은 R² 0.9818·약 623초였다. CNN은 R²가 약간 낮은 대신 5배 이상 빠르다 — "정확도를 조금 양보하고 속도를 크게 얻는" 트레이드오프다.

### A-2. 시계열을 Conv1D로 — RNN과 같은 입력

**Conv1D**는 시간축(1차원) 방향으로 커널(필터)이 슬라이딩하며 지역 패턴을 뽑는 합성곱이다. 입력이 RNN과 똑같은 3차원 `(N, 타임스텝, 피처)`라서, **모델 층만 바꾸면 RNN을 Conv1D로 재구성**할 수 있다.

```python
model.add(Conv1D(filters=128, kernel_size=2, input_shape=(피처수, 1)))
model.add(Conv1D(128, 2))
model.add(GlobalAveragePooling1D())   # 또는 Flatten → 3D를 2D로
model.add(Dense(...))
model.add(Dense(출력))
```

- **`Conv1D(filters, kernel_size, input_shape)`** : `filters`는 뽑을 특성 수, `kernel_size`는 한 번에 보는 타임스텝 수(2면 연속 2개씩).
- **`input_shape=(10)`은 에러다.** `(10)`은 그냥 정수(괄호는 계산용)이고, 튜플은 쉼표가 필요하다. 게다가 Conv1D 입력은 3차원이라 피처 1을 붙여 `(피처수, 1)`로 쓴다.
- **Conv1D 출력은 3차원**이라 Dense로 넘기기 전에 `Flatten`(전부 펼침) 또는 `GlobalAveragePooling1D`(타임스텝 축 평균으로 압축, 파라미터 적음)로 2차원으로 바꾼다.

**데이터 종류가 성능을 가른다.** 표 데이터(wine 약 0.98 등)와 간단한 수열에는 Conv1D가 잘 맞고, RNN과 비슷하거나 살짝 더 정확하면서 병렬 처리가 가능해 더 빠르다. 반면 **이미지를 1D 시퀀스로 펴면 공간 구조가 깨져 실패**한다(fashion 약 0.10, 사실상 랜덤). "이미지는 Conv2D, 시계열·표는 Conv1D"가 요지다. 이미지를 Conv1D로 바꿀 때는 기존 Conv2D·그 뒤 Flatten을 모두 삭제해야 한다(4D와 3D는 섞을 수 없다).

### A-3. 모델별 차원 총정리 (Conv1D 포함)

| 구분 | Dense | Conv2D | Conv1D | RNN | Embedding |
|---|---|---|---|---|---|
| 입력 차원 | 2 이상 | 4 | 3 | 3 | 2 |
| 출력 차원 | 2 이상 | 4 | 3 | 2 | 3 |
| input_shape 숫자 개수 | 1 | 3 (H,W,C) | 2 (타임스텝,피처) | 2 (타임스텝,피처) | input_dim·output_dim |

Conv1D와 RNN은 입력 차원·input_shape가 똑같아 서로 교체가 쉽다. Embedding은 2D 입력 → 3D 출력으로, 뒤에 RNN/Conv1D를 자연스럽게 연결한다.

### A-4. 앙상블 — 여러 입력 합치기, 출력 분기

**앙상블**은 여러 모델(입력)을 `Concatenate`로 합쳐 하나로 만든 모델이다. 입력 종류가 여러 개일 때 쓴다. 함수형 API로 구성한다.

```python
# 입력마다 별도 모델 — Input의 피처 수를 각 데이터에 맞춘다
input1 = Input(shape=(2,)); ...; output1 = Dense(5)(...)   # 모델1 (피처 2)
input2 = Input(shape=(3,)); ...; output2 = Dense(3)(...)   # 모델2 (피처 3)

from tensorflow.keras.layers import Concatenate
merge = Concatenate()([output1, output2])    # 출력들을 이어붙임
last  = Dense(1)(Dense(10)(merge))

model = Model(inputs=[input1, input2], outputs=last)   # 입력은 리스트
model.fit([x1_train, x2_train], y_train, ...)          # 입력도 리스트
```

- **각 `Input(shape=...)`의 피처 수를 데이터와 맞춘다.** 안 맞으면 "expected (None,2) found (None,3)" 에러가 난다.
- **출력을 여러 갈래로 분기**할 수 있다(예: y1·y2 동시 예측). 이때 타깃도 `[y1, y2]` 리스트로 넘기고, 예측은 `y1_pred, y2_pred = model.predict(...)`로 언패킹해 받는다.

**앙상블에서 자주 난 에러.**

| 에러 | 원인 | 해결 |
|---|---|---|
| stratify ValueError | 회귀 y에 `stratify=y`(분류용) | stratify 삭제 |
| expected (None,2) found (None,3) | Input 피처 수 불일치 | 각 Input을 데이터에 맞춤 |
| multiple values for batch_size | 출력 여러 개인데 y를 리스트로 안 묶음 | `[y1_train, y2_train]`로 |
| predict 결과 엉뚱 | 출력 2개 리스트를 한 변수에 담고 `[-1]` | `y1,y2 = model.predict(...)` 언패킹 |

ensemble1(입력 2·출력 1) → ensemble2(입력 3·출력 1) → ensemble3(입력 3·출력 2, 분기) 순으로 확장했다.

## B. RAG 파이프라인 — 문서를 벡터로 저장·검색·생성

### B-1. RAG 핵심 플로우

```
① 불러오기 → ② 청킹 → ③ 임베딩 → ④ VectorDB 저장
                                        ↓ 불러오기
질문 → ⑤ retriever로 유사 문서 검색 → ⑥ 프롬프트 {context}에 삽입 → ⑦ LLM 생성(answer)
                                        ↓
                                   Gradio 웹 챗봇
```

6주차에 이 흐름을 **검색까지 → 검색+LLM 생성(RAG 완성) → 웹 챗봇**으로 완성하고, VectorDB(Chroma·FAISS)·문서 종류(txt·PDF)·임베딩(OpenAI·HuggingFace)을 바꿔가며 반복했다.

### B-2. ① 불러오기 → ② 청킹

```python
# txt
from langchain_community.document_loaders import TextLoader
loader = TextLoader(path + "samsung_outlook.txt", encoding="utf-8")   # 한글이라 utf-8

# PDF (논문 등)
from langchain_community.document_loaders import PyPDFLoader
pdf_docs = PyPDFLoader(path + "Attention_is_all_you_need.pdf").load()  # 페이지 단위 리스트
print(len(pdf_docs))   # 15 (15페이지)

# 청킹
from langchain_text_splitters import RecursiveCharacterTextSplitter
Text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=300, chunk_overlap=100,
    separators=["\n\n", "\n", " ", ""],
)
split_docs = Text_splitter.split_documents(pdf_docs)   # 15페이지 → 205 청크
```

- **`PyPDFLoader().load()`는 PDF를 페이지 단위 리스트로 반환**한다. 결과가 리스트라 `pdf_docs.load_and_split(...)`은 에러고, `Text_splitter.split_documents(pdf_docs)`로 청킹한다.
- **청킹의 `chunk_size=300`은 상한**이다. `separators` 순서(문단→줄→단어→글자)로 의미 경계를 지키며 자르므로, 각 청크 길이가 300 딱이 아니라 300 이하로 들쭉날쭉하다. `chunk_overlap=100`은 청크끼리 100자 겹쳐 문맥 끊김을 완화한다.
- 여러 파일은 `glob("*.txt")`로 경로를 모아 반복 `load()`한 뒤 `split_documents`로 한 번에 자른다.
- document는 `page_content`(본문) + `metadata`(파일 경로 등)로 이루어진다.

### B-3. ③ 임베딩 — OpenAI(API) ↔ HuggingFace(로컬)

**임베딩**은 텍스트를 의미를 담은 벡터로 바꾸는 것이다. 두 방식이 있다.

```python
# OpenAI (API 호출)
from langchain_openai import OpenAIEmbeddings
embeddings = OpenAIEmbeddings(model="text-embedding-3-small", api_key=api_key, base_url=base_url)

# HuggingFace (로컬 실행)
from langchain_huggingface.embeddings import HuggingFaceEmbeddings
embeddings = HuggingFaceEmbeddings(model_name="BAAI/bge-m3", model_kwargs={"device": "cpu"})
```

| | OpenAIEmbeddings | HuggingFaceEmbeddings |
|---|---|---|
| 실행 | API(서버 호출, 키·네트워크 필요) | 로컬(내 PC에서 모델 다운로드·실행) |
| 비용 | 사용량 과금 | 무료(내 자원 사용) |
| 예시(차원) | text-embedding-3-small(1536)/large(3072) | bge-m3(1024), Qwen3-Embedding-0.6B(1024) |

- HuggingFace 모델은 처음 실행 시 자동 다운로드되고 이후 캐시를 쓴다. `device`로 cpu/gpu를 고른다.
- **임베딩을 바꾸면 VectorDB를 새로 만들어야 한다.** OpenAI(1536차원)로 저장한 DB를 bge-m3(1024차원)로는 못 읽는다(차원 불일치). 저장할 때와 불러올 때 임베딩이 같아야 한다.

### B-4. ④ 저장 / ⑤ 불러오기 — Chroma vs FAISS

| | Chroma | FAISS |
|---|---|---|
| 제공 | langchain-chroma | Facebook(faiss) + langchain-community |
| 저장 | `Chroma.from_documents(..., persist_directory, collection_name)` | `FAISS.from_documents(...)` → `save_local(folder_path, index_name)` |
| 불러오기 | `Chroma(embedding_function=..., persist_directory, collection_name)` | `FAISS.load_local(..., allow_dangerous_deserialization=True)` |

```python
# Chroma 저장
db = Chroma.from_documents(documents=split_docs, embedding=embeddings,
                           persist_directory="./_db/Chroma12/", collection_name="croma12")
# Chroma 불러오기 (from_documents 아님!)
db = Chroma(embedding_function=embeddings, persist_directory="./_db/Chroma12/", collection_name="croma12")

# FAISS 저장
import faiss
faiss_index = faiss.IndexFlatL2(len(embeddings.embed_query("hello world")))  # L2거리 인덱스
db = FAISS.from_documents(documents=split_docs, embedding=embeddings)
db.save_local(folder_path=DB_PATH, index_name="faiss_index19")
# FAISS 불러오기
db = FAISS.load_local(DB_PATH, index_name="faiss_index19", embeddings=embeddings,
                      allow_dangerous_deserialization=True)
```

- **저장은 `from_documents`, 불러오기는 열기 전용 생성자**(Chroma는 `Chroma(embedding_function=...)`, FAISS는 `load_local`)로 구분한다. 불러올 때 경로·이름·임베딩이 저장 때와 같아야 한다.
- **저장은 1회만 하고 주석 처리**한 뒤 이후엔 불러와 쓴다. 매번 재임베딩하면 느리고 비용이 든다.
- **`faiss.IndexFlatL2(차원)`** 은 L2(유클리드) 거리로 유사도를 재는 인덱스다. 차원은 임베딩 차원과 같아야 한다.
- **`allow_dangerous_deserialization=True`** 는 FAISS가 pickle로 저장돼 불러올 때 코드 실행 위험이 있어 명시적 허용이 필요하다. 내가 만든 신뢰할 수 있는 파일일 때만 쓴다.
- VectorDB만 바뀔 뿐, 이후 retriever→RAG 체인→Gradio 흐름은 Chroma·FAISS가 동일하다.

### B-5. ⑤ 검색 → ⑥⑦ 생성 — RAG 체인

검색만 하던 것에 LLM을 붙여 "근거 기반 답변 생성"까지 완성한다.

```python
# 검색기
retriever = db.as_retriever(search_kwargs={"k": 2})   # 유사 문서 k개

# 답변 생성 LLM
from langchain_openai import ChatOpenAI
model = ChatOpenAI(model="gpt-5-nano", temperature=0, max_tokens=1000, api_key=api_key, base_url=base_url)

# RAG 체인
from langchain_core.prompts import ChatPromptTemplate
from langchain_classic.chains.combine_documents import create_stuff_documents_chain
from langchain_classic.chains import create_retrieval_chain

prompt = ChatPromptTemplate.from_template("""
다음 컨텍스트를 바탕으로 질문에 답변해 주세요.
컨텍스트 관련 정보가 없다면 "주어진 정보로는 답변할 수 없습니다"라고 말해주세요.
컨텍스트 : {context}
질문 : {input}
""")

docu_chain = create_stuff_documents_chain(model, prompt)    # 프롬프트+모델 (검색문서를 context에 채움)
rag_chain  = create_retrieval_chain(retriever, docu_chain)  # 검색 + 생성 = RAG

response = rag_chain.invoke({"input": query})
print(response.keys())     # dict_keys(['input', 'context', 'answer'])
print(response["answer"])  # 최종 답변
```

- **`similarity_search(질문, k)` / `as_retriever`** : 질문을 벡터로 바꿔 가장 가까운 청크 k개를 가져온다(기본 4). retriever는 체인에 끼우기 좋은 표준 인터페이스다.
- **`ChatOpenAI`** 는 답변 생성용 LLM(임베딩 모델과 별개)이다. `temperature`는 0(있는 그대로)~1(창의적), `max_tokens`는 답 길이 상한이다.
- **`create_stuff_documents_chain`** 은 검색된 문서를 프롬프트의 `{context}`에 밀어넣고(stuff), **`create_retrieval_chain`** 은 검색(retriever) → 생성(docu_chain)을 하나로 묶는다. 결과는 `input·context·answer` 딕셔너리다.
- **RAG의 핵심 원리**는 "검색한 문서를 프롬프트에 넣어 그 근거로만 답하게 한다"이다. 프롬프트에 "정보 없으면 답변할 수 없다"를 넣어 환각(지어내기)을 억제한다. 반대로 "지어내라"는 프롬프트는 RAG 목적과 정반대인 안티패턴으로, 프롬프트가 답을 좌우함을 보여주는 실습용일 뿐 실무에선 쓰지 않는다.

### B-6. Gradio 웹 챗봇

```python
import gradio as gr

def answer_invoke(message, history):      # message=입력, history=대화기록
    response = rag_chain.invoke({"input": message})
    return response["answer"]

demo = gr.ChatInterface(fn=answer_invoke, title="Test Chat Bot")
demo.launch()        # launch(share=True)면 외부 공유 링크 생성
```

- **`gr.ChatInterface(fn=함수)`** 는 함수 하나만 넘기면 채팅 UI를 자동 생성한다. 함수는 `(message, history)`를 받아 답 문자열을 반환한다.
- VectorDB(Chroma/FAISS)·문서(txt/PDF)·임베딩(OpenAI/HF)을 바꿔도 이 챗봇 연결부는 동일하다.

## 6주차 한 줄 요약

> **합성곱으로 시계열 다루기** — 시계열을 CNN으로 쓰려면 모델 안 `Reshape(144,13,1)`로 이미지화 후 Conv2D를 쌓되 batch를 작게·MaxPooling으로 OOM을 피한다(LSTM보다 R²는 약간 낮지만 훨씬 빠름). Conv1D는 RNN과 같은 3D 입력이라 층만 바꿔 재구성되며, 표·시계열엔 잘 맞지만 이미지엔 부적합하다. **앙상블**은 여러 입력을 Concatenate로 합치고(입력은 리스트), 출력을 분기하면 타깃·predict도 리스트로 다룬다.
> **RAG 완성** — 불러오기(TextLoader/PyPDFLoader) → 청킹(RecursiveCharacterTextSplitter) → 임베딩(OpenAI API 또는 HuggingFace 로컬, 바꾸면 DB 재저장) → VectorDB 저장·불러오기(Chroma/FAISS, 저장은 from_documents·불러오기는 열기 전용) → retriever 검색 → 프롬프트 {context}에 넣어 LLM 생성(create_stuff_documents_chain + create_retrieval_chain, 결과 input·context·answer) → Gradio 챗봇. VectorDB·문서·임베딩이 바뀌어도 검색→생성→챗봇 흐름은 동일하며, 프롬프트가 답을 좌우한다.
