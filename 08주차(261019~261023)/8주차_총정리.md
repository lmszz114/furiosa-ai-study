## A. LangGraph — AI 작업 흐름을 그래프로

지금까지의 RAG는 "검색 → 생성"으로 한 방향으로 흐르는 직선 파이프라인이었다. 실제 서비스는 **반복·분기·병렬**(검색이 부실하면 다시, 품질을 평가해 분기, 두 모델에 동시에)이 필요하다. **LangGraph는 작업 단계를 블록으로 두고 화살표로 이어 이런 흐름을 설계하는 도구**다(공장 컨베이어 벨트에 비유).

### A-1. 핵심 3요소 — 상태 · 노드 · 엣지

- **상태(State)**: 모든 단계가 함께 읽고 쓰는 **공유 화이트보드**. `TypedDict`로 "어떤 칸이 있는지" 틀을 정한다.
- **노드(Node)**: 상태를 읽어 일을 하고 결과를 상태에 적는 **작업 단위(함수 하나)**.
- **엣지(Edge)**: 노드 사이를 잇는 **화살표(순서)**. 모든 그래프는 `START`에서 시작해 `END`에서 끝난다.

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END, add_messages

class State(TypedDict):
    messages : Annotated[list, add_messages]   # 대화가 '쌓이는' 칸

def chatbot(state: State):
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(State)
builder.add_node("chatbot", chatbot)       # 노드 등록
builder.add_edge(START, "chatbot")         # 엣지로 순서 연결
builder.add_edge("chatbot", END)
graph = builder.compile()                  # 실행 가능한 그래프로 완성
response = graph.invoke({"messages": [("user", query)]})
```

- **`TypedDict`**: 항목 이름·값의 종류를 미리 정한 "딕셔너리 설계도". LangGraph의 상태가 이것으로 정의된다.
- **`Annotated[list, add_messages]`**: "이 칸은 리스트인데, 값을 더할 때 `add_messages` 규칙(리듀서)으로 쌓는다"는 뜻. **`add_messages`** 는 메시지 목록을 합치되 **id가 다르면 둘 다 남기고, 같으면 뒤의 것으로 교체**한다 → 대화가 누적된다. (상태 키를 `message`/`messages`로 섞으면 값이 어긋나 오류가 나므로 **`messages`로 통일**한다.)
- 노드를 여럿 두고 `add_edge`로 이으면 `START→prepare→chatbot→finish→END`처럼 여러 단계를 거치는 **직선 그래프**가 된다.

### A-2. 도구 호출 — ToolNode · 조건부 엣지

LLM이 모르는 **실시간·최신 정보**(오늘 주가 등)는 **외부 도구(웹 검색)** 로 가져온다. "아는 건 바로 답하고, 모르는 건 검색 도구를 꺼내 쓰는" 방식이다.

```python
from langgraph.prebuilt import ToolNode, tools_condition

llm_with_tools = llm.bind_tools([web_search])   # LLM에 도구 목록을 쥐어줌

builder.add_node("chatbot", chatbot)
builder.add_node("tools", ToolNode([web_search]))   # 도구를 실제 실행하는 노드
builder.add_edge(START, "chatbot")
builder.add_conditional_edges("chatbot", tools_condition)  # 도구 필요하면 tools, 아니면 END
builder.add_edge("tools", "chatbot")   # 도구 실행 후 다시 LLM으로 (순환)
```

- **`bind_tools`**: LLM에 도구 목록을 쥐어주면, LLM이 "도구가 필요한지" 판단해 **도구 호출 요청(tool_calls)** 을 만든다.
- **`ToolNode`**: LLM이 요청한 도구를 **실제로 실행**하는 노드.
- **`tools_condition`**: LangGraph가 제공하는 **조건부 엣지** 함수. 직전 답에 도구 호출이 **있으면 `tools`로, 없으면 `END`로** 보낸다. `tools → chatbot`으로 되돌리면 "LLM ↔ 도구" 왕복(순환)이 완성된다.
- 검색 도구는 **Tavily**(API 키 필요)·**DuckDuckGo**(무료, `ddgs`) 등으로 바꾸거나 여러 개를 함께 붙일 수 있고, 그래프 구조는 그대로 둔 채 도구만 교체하면 된다. 만든 그래프는 `draw_mermaid_png()`로 그림 저장(또는 `BytesIO`+`matplotlib`로 화면 표시)해 구조를 확인한다.

### A-3. 메모리(체크포인터) · 병렬 실행

**메모리** — 기본 `invoke`는 매번 독립 실행이라 이전 대화를 기억하지 못한다. **체크포인터**를 달면 기억한다.

```python
from langgraph.checkpoint.memory import InMemorySaver
memory = InMemorySaver()
graph = builder.compile(checkpointer=memory)          # ② 기억 장치 연결
config = {"configurable": {"thread_id": "user01"}}    # ③ 대화방 번호
graph.invoke({"messages": [("user", "내 이름은 윤영선이야.")]}, config=config)
graph.invoke({"messages": [("user", "내 이름이 뭐야.")]}, config=config)  # "윤영선" 기억
```

- **`InMemorySaver`**: 상태(대화)를 **RAM에 저장**하는 기억 장치(프로그램을 끄면 사라짐). **`thread_id`** 는 대화방을 구분하는 번호로, 같은 번호면 대화가 이어지고 다른 번호면 별개의 새 대화가 된다(여러 사용자 분리).

**병렬 실행** — 서로 의존하지 않는 작업은 **START에서 여러 노드로 갈라 동시에** 돌리고, 한 노드(`merge`)로 모아 합친다.

```python
builder.add_edge(START, "search")      # ┐ 동시에
builder.add_edge(START, "analysis")    # ┘ 실행
builder.add_edge("search", "merge")    # ┐ merge로
builder.add_edge("analysis", "merge")  # ┘ 모임 (둘 다 끝나야 실행)
```

- 병렬 노드는 **상태의 서로 다른 칸**(`search_result`·`analysis_result`)에 써서 충돌을 피한다(같은 칸에 동시에 쓰면 리듀서가 없는 한 충돌). `merge`가 두 칸을 읽어 합친다. (예: 웹 검색 + LLM 자체 분석을 동시에 수행 후 통합)

### A-4. 병렬 결과를 LLM이 종합

`merge` 노드가 두 결과를 **기계적으로 이어 붙이는 대신, LLM에게 넘겨 종합**하게 하면 매끄러운 최종 답변이 된다.

```python
def merge_agent(state):
    prompt = f"""다음 두 결과를 종합해 최종 답변을 작성해줘.
[웹 검색 결과] {state["search_result"]}
[AI 분석 결과] {state["analysis_result"]}
검색 결과를 우선 참고하고, 최신 정보와 기존 분석을 구분해서 설명해줘."""
    return {"messages": [llm.invoke(prompt)]}
```

- 통합 기준을 프롬프트로 지시하면("검색 우선 참고, 최신/기존 구분"), 실시간 검색과 배경지식이 역할 구분된 답이 나온다. 병렬로 서로 다른 관점을 모으고 LLM이 **편집자처럼 종합**하는 패턴이다.

## B. 머신러닝 — 트리 모델과 특성 중요도

목요일 뒷부분부터 딥러닝(Keras)과 별개인 **머신러닝(트리 기반 모델)** 으로 넘어간다. 라이브러리가 달라 전용 가상환경을 새로 만든다(`conda create -n ml-311 python==3.11`, `pip install xgboost scikit-learn pandas`).

### B-1. 트리 모델 4종 · 특성 중요도

```python
from sklearn.tree import DecisionTreeClassifier
from sklearn.ensemble import RandomForestClassifier, GradientBoostingClassifier
from xgboost import XGBClassifier

models = [DecisionTreeClassifier(), RandomForestClassifier(),
          GradientBoostingClassifier(), XGBClassifier()]
for model in models:
    model.fit(x_train, y_train)
    print(model.score(x_test, y_test))
    print(model.feature_importances_)   # 특성 중요도
```

- **트리 모델 4종**(모두 "데이터를 조건으로 나눠가며 예측"):
  - **DecisionTree(결정 트리)**: 기본 단위. 한 그루라 단순하고 과적합되기 쉽다.
  - **RandomForest**: 결정 트리 여러 그루의 **다수결**(앙상블). 더 안정적.
  - **GradientBoosting**: 트리를 순서대로 쌓되 **앞 트리가 틀린 부분을 다음 트리가 보완**. 보통 성능 높음.
  - **XGBoost**: 그래디언트 부스팅을 빠르고 강력하게 구현. 실무·대회에서 많이 씀.
- **`feature_importances_`(특성 중요도)**: 트리 모델은 학습 후 **어떤 입력 변수가 예측에 얼마나 기여했는지**를 0~1(합 1)로 알려준다. 신경망에는 없는 트리 모델 고유의 해석 도구다. 중요 변수를 알면 모델을 단순화하거나 결과를 설명하는 근거로 쓴다.
- **분류/회귀 짝**: `Classifier`↔`Regressor`(DecisionTreeClassifier↔Regressor 등), 평가는 분류=acc·회귀=R², 회귀엔 `stratify`를 쓰지 않는다.
- **XGBoost 중요도 두 기준**: **F score(weight)** = 분기 조건으로 쓰인 **빈도(횟수)**, **Gain score** = 분기로 **줄인 손실(실제 기여)**. 자주 쓰여도 이득은 작을 수 있어 둘이 다를 수 있다. `plot_importance(model, importance_type='weight'/'gain')`로 막대그래프 시각화.

## 한 주 핵심 한 줄

> **LangGraph**는 AI 작업 흐름을 그래프로 설계하는 도구로, **상태(State, `TypedDict`+`add_messages`)·노드(함수)·엣지(`START→…→END`)** 3요소로 `StateGraph`를 만들어 `compile`·`invoke`한다. **도구 호출**은 `bind_tools`로 LLM에 도구를 쥐어주고 **`ToolNode`**(실행)와 조건부 엣지 **`tools_condition`**(도구 필요하면 tools, 아니면 END)으로 "LLM↔도구" 순환을 만든다(Tavily·DuckDuckGo 교체 가능). **메모리**는 `InMemorySaver` 체크포인터와 `thread_id`로 대화를 기억시키고, **병렬 실행**은 START에서 여러 노드로 갈라 각자 다른 상태 칸에 쓰고 `merge`로 모으며(LLM 종합까지) 처리한다. 후반에는 **머신러닝 트리 모델**(DecisionTree·RandomForest·GradientBoosting·XGBoost)로 넘어가, 신경망엔 없는 **특성 중요도(`feature_importances_`, 합 1)** 로 어떤 변수가 중요했는지 파악하고 XGBoost의 F score(빈도)·Gain score(실제 기여) 두 기준을 비교했다.
