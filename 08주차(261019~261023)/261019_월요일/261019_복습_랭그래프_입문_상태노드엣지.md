## 0. LangGraph란 무엇이고 왜 쓰는가

지금까지의 RAG는 "검색 → 생성"으로 한 방향으로 흐르는 파이프라인이었다. 질문이 들어오면 문서를 찾고, 그 문서로 답을 만들고, 끝난다. 한 번 지나가면 되돌아오지 않는 직선 흐름이다.

그런데 실제 AI 서비스는 더 복잡한 흐름이 필요하다. 예를 들어 "검색 결과가 부실하면 질문을 바꿔 다시 검색하기", "답변 품질을 평가해 충분하면 끝내고 부족하면 다시 만들기", "GPT와 Claude 두 모델에 동시에 물어보고 결과를 합치기" 같은 **반복·분기·병렬**이다. 직선 파이프라인으로는 이런 흐름을 만들기 어렵다.

**LangGraph는 AI의 작업 흐름을 '그래프(순서도)'로 그려서 만드는 도구다.** 작업 단계 하나하나를 블록으로 두고, 블록 사이를 화살표로 이어 전체 흐름을 설계한다. 화살표가 갈라지거나 되돌아오게 만들 수 있어, 조건 분기와 반복이 자연스럽게 표현된다.

**비유하자면 공장의 컨베이어 벨트다.** 작업대(블록)들이 늘어서 있고, 제품(데이터)이 벨트(화살표)를 따라 작업대를 거치며 완성된다. 어떤 작업대에서는 검사 결과에 따라 "통과 라인"과 "재작업 라인"으로 갈라지기도 한다. LangGraph로 만드는 것이 바로 이 작업 흐름도다.

## 1. 핵심 3요소 — 상태(State) · 노드(Node) · 엣지(Edge)

LangGraph로 흐름을 만들려면 세 가지만 알면 된다.

**① 상태(State) — 모두가 함께 보는 '공유 화이트보드'.**
작업하는 모든 단계가 함께 보고 함께 적는 하나의 메모판이다. 질문, 지금까지의 대화, 중간 계산 결과 등 흐름 전체에서 공유해야 할 정보를 여기에 담는다. 각 단계는 이 화이트보드를 읽어서 일하고, 결과를 다시 화이트보드에 적는다.

**② 노드(Node) — 실제로 일을 하는 '작업자(작업 단계)'.**
화이트보드(상태)를 읽어서 뭔가를 처리하고, 그 결과를 화이트보드에 다시 적는 하나의 작업 단위다. "LLM에게 질문해 답을 받는다", "검색을 한다", "결과를 평가한다" 같은 각각의 일이 하나의 노드가 된다. 코드에서는 함수 하나가 노드 하나다.

**③ 엣지(Edge) — 다음 작업자에게 넘기는 '화살표(순서)'.**
어느 노드 다음에 어느 노드로 갈지를 정하는 연결선이다. "A 작업이 끝나면 B 작업으로" 같은 순서를 만든다. 조건에 따라 갈라지는 화살표(조건부 엣지)도 만들 수 있는데, 이건 6번에서 다룬다.

**흐름의 시작과 끝 — START와 END.**
모든 그래프는 `START`(시작 지점)에서 출발해 `END`(끝 지점)에서 멈춘다. START에서 첫 노드로 엣지를 잇고, 마지막 노드에서 END로 엣지를 이으면 흐름이 완성된다.

```
[START] → (노드1) → (노드2) → ... → [END]
           화이트보드(State)를 읽고 쓰며 진행
```

## 2. lg01_TypedDict — 상태의 '틀' 만들기

상태(화이트보드)는 파이썬 딕셔너리(`{"키": 값}`)로 되어 있다. 그런데 아무 키나 막 넣으면 실수가 생기기 쉬워서, **"이 상태에는 어떤 항목이 들어가고 각각 어떤 종류의 값인지" 틀을 미리 정해둔다.** 그 틀을 만드는 도구가 `TypedDict`다.

```python
from typing import Dict, TypedDict

# 그냥 딕셔너리 — 틀이 없음
sample_dict : Dict[str, str] = {
    'name' : '김말똥', 'age' : 39, 'job' : '회사원'
}

# TypedDict — 틀을 정한 딕셔너리
class Person(TypedDict):
    name : str     # name은 문자열
    age : int      # age는 정수
    job : str      # job은 문자열

person = Person(name='홍길동', age=40, job='도적')
print(person)   # {'name': '홍길동', 'age': 40, 'job': '도적'}

person2 : Person = {'name' : '김개똥', 'age' : 20, 'job' : '전사'}
print(person2)
```

- **`TypedDict`는 "항목 이름과 값의 종류를 미리 정해둔 딕셔너리 설계도"다.** `Person`이라는 틀을 만들면 "이 딕셔너리에는 name·age·job이 들어가고, age는 숫자다"가 정해진다. 내용물은 보통 딕셔너리와 똑같지만, 틀이 있어 코드를 짤 때 오타나 빠진 항목을 미리 잡을 수 있다.
- **LangGraph의 상태(State)가 바로 이 `TypedDict`로 정의된다.** 화이트보드에 어떤 칸이 있는지를 이 틀로 선언하는 것이다. 다음 파일부터 상태를 만들 때 이 문법을 쓴다.

(실행만 하는 기초 예제라 `age`에 문자열 틀을 줬지만 숫자를 넣는 등 틀과 실제 값이 어긋나도 파이썬은 그냥 실행된다. `TypedDict`의 틀은 강제가 아니라 코드 작성·검사를 돕는 안내 역할이다.)

## 3. lg02_add_messages — 대화가 쌓이는 규칙(리듀서)

상태의 화이트보드에 새 내용을 적을 때, **기존 내용을 지우고 새로 쓸지, 아니면 아래에 이어서 쌓을지**를 정해야 한다. 대화 기록은 지워지면 안 되고 계속 쌓여야 하므로, "쌓기" 규칙을 지정하는데 그것이 `add_messages`다.

```python
from typing import Annotated, TypedDict
from langgraph.graph import add_messages

class MyDate(TypedDict):
    messages : Annotated[list, add_messages]   # messages 칸은 'add_messages 규칙'으로 쌓는다

from langchain_core.messages import AIMessage, HumanMessage

# 서로 다른 id
msg1 = [HumanMessage(content="안녕", id='1')]
msg2 = [AIMessage(content="방가", id='2')]
result2 = add_messages(msg1, msg2)
print(result2)   # 두 메시지가 모두 남음 (id가 달라서 둘 다 보존)

# 같은 id
msg3 = [HumanMessage(content="안녕", id='3')]
msg4 = [AIMessage(content="방가", id='3')]
result2 = add_messages(msg3, msg4)
print(result2)   # 하나만 남음 (id가 같아서 뒤의 것이 앞의 것을 교체)
```

- **`Annotated[list, add_messages]`는 "이 칸은 리스트인데, 값을 더할 때 `add_messages` 규칙을 쓴다"는 뜻이다.** `Annotated`는 "자료형(list)에 추가 설명(add_messages)을 붙이는" 문법이다. 여기서 추가 설명이 곧 "어떻게 쌓을지"의 규칙이고, 이런 쌓기 규칙을 **리듀서(reducer)** 라고 부른다.
- **`add_messages`의 동작**: 두 메시지 목록을 합치되, **id가 다르면 둘 다 남기고(이어붙이기), id가 같으면 뒤의 것으로 교체(업데이트)** 한다. 그래서 첫 번째 예(id 1·2)는 두 개가 모두 남고, 두 번째 예(둘 다 id 3)는 하나로 합쳐진다.
- 이 규칙 덕분에 챗봇이 대화를 주고받을 때 새 메시지가 기존 대화에 계속 **누적**된다. 상태의 `messages` 칸에 이 리듀서를 달아두면, 각 노드가 메시지를 반환할 때마다 알아서 쌓인다.

**메시지의 종류**: `HumanMessage`(사람이 한 말), `AIMessage`(AI가 한 말)로 누가 한 말인지 구분한다. 대화는 이 메시지들의 목록으로 관리된다.

## 4. lg03_chatbot — 가장 단순한 그래프 (상태 + 노드 1개 + 엣지)

상태·노드·엣지를 모두 써서 가장 단순한 챗봇 그래프를 만든다. 흐름은 `START → chatbot → END` 한 줄이다.

```python
# LLM 준비 (답변 생성 모델)
llm = ChatOpenAI(model_name='gpt-5.6-terra', temperature=0, max_tokens=1000,
                 api_key=api_key, base_url=base_url)

from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

# 1. 상태 정의 — 화이트보드에 어떤 칸이 있는지
class State(TypedDict):
    messages : Annotated[list, add_messages]   # 대화는 쌓인다
    aaa : str
    bbb : str
    ccc : int

# 2. 노드 정의 — 상태를 읽어 LLM에 물어보고, 답을 상태에 적는다
def chatbot(state : State):
    return {"messages" : [llm.invoke(state["messages"])]}

# 3. 그래프 구성 — 상태 틀로 그래프를 만들고 노드를 등록
graph_01 = StateGraph(State)
graph_01.add_node("chatbot", chatbot)

# 4. 엣지 추가 — 시작→chatbot→끝
graph_01.add_edge(START, "chatbot")
graph_01.add_edge("chatbot", END)

# 5. 컴파일 — 설계도를 실행 가능한 그래프로 완성
graph = graph_01.compile()

# 6. 실행
query = "삼성전자의 주가를 예측해줘"
response = graph.invoke({"messages" : [("user", query)]})

print(response['messages'][1].content)   # LLM 답변 내용
print(response['messages'][0].type)      # human (내 질문)
print(response['messages'][1].type)      # ai (AI 답변)
```

흐름을 순서대로 보면:

- **상태 정의** — `State`라는 화이트보드 틀을 만든다. `messages` 칸은 대화가 쌓이도록 `add_messages` 규칙을 달았다. (`aaa·bbb·ccc`는 틀에 칸을 여러 개 둘 수 있음을 보여주는 예시로, 이 챗봇에선 쓰지 않는다.)
- **노드 정의** — `chatbot` 함수가 노드다. 상태에서 `messages`(지금까지의 대화)를 꺼내 `llm.invoke`로 LLM에 넘기고, 받은 답을 `{"messages": [...]}`로 반환한다. 반환하면 그 답이 상태의 `messages`에 쌓인다.
- **그래프 구성** — `StateGraph(State)`로 상태 틀을 기반으로 빈 그래프를 만들고, `add_node`로 작업자(chatbot)를 등록한다.
- **엣지 추가** — `add_edge(START, "chatbot")`, `add_edge("chatbot", END)`로 "시작 → chatbot → 끝" 순서를 잇는다.
- **컴파일** — `compile()`로 설계도를 실제 실행할 수 있는 그래프로 굳힌다.
- **실행** — `invoke`에 첫 메시지를 넣어 그래프를 돌린다. `("user", query)`는 "사람이 한 말"이라는 뜻으로, 내부에서 `HumanMessage`로 변환된다.

**결과 읽기**: 실행이 끝나면 상태의 `messages`에는 `[사람 질문, AI 답변]` 두 개가 쌓여 있다. 그래서 `messages[0]`은 내 질문(type이 `human`), `messages[1]`은 AI 답변(type이 `ai`)이고, `messages[1].content`가 실제 답변 글이다.

(이 파일에서 상태 키를 `message`(단수)와 `messages`(복수)로 섞어 쓰면, 넣은 값과 읽는 칸이 어긋나 LLM에 빈 메시지가 전달되고 `messages 배열이 필요합니다` 오류가 난다. 상태 정의·노드·실행에서 **키 이름을 `messages`로 통일**해야 한다.)

## 5. lg04_node_edge — 노드 여러 개를 순서대로 잇기

노드를 세 개로 늘려 `START → prepare → chatbot → finish → END`로 잇는다. 여러 작업 단계를 차례로 거치는 흐름을 만드는 연습이다.

```python
# 2. 노드 정의 — 세 개의 작업자
def prepare(state : State):
    return {"messages" : [AIMessage(content="질문을 접수했습니다.")]}

def chatbot(state : State):
    return {"messages" : [llm.invoke(state["messages"])]}

def finish(state : State):
    return {"messages" : [AIMessage(content="답변 처리가 완료되었습니다.")]}

# 3. 그래프 구성 — 노드 세 개 등록
graph_01 = StateGraph(State)
graph_01.add_node("prepare", prepare)
graph_01.add_node("chatbot", chatbot)
graph_01.add_node("finish", finish)

# 4. 엣지 추가 — 네 단계를 순서대로
graph_01.add_edge(START, "prepare")
graph_01.add_edge("prepare", "chatbot")
graph_01.add_edge("chatbot", "finish")
graph_01.add_edge("finish", END)

graph = graph_01.compile()

response = graph.invoke({"messages" : [("user", query)]})

# 7. 결과 출력 — 쌓인 메시지를 순서대로
for i, msg in enumerate(response['messages']):
    print(f"[{i}] {msg.type} : {msg.content}")
```

- **노드 세 개가 순서대로 상태에 메시지를 쌓는다.** `prepare`는 "질문을 접수했습니다"를 추가하고, `chatbot`은 그때까지의 대화를 LLM에 넘겨 답변을 추가하고, `finish`는 "답변 처리가 완료되었습니다"를 추가한다. 각 노드가 반환하는 메시지가 `add_messages` 규칙으로 차곡차곡 쌓인다.
- **엣지로 네 단계를 한 줄로 잇는다.** `START → prepare → chatbot → finish → END`. 앞 노드가 끝나면 엣지를 따라 다음 노드로 넘어간다.
- **최종 상태의 `messages`에는 4개가 순서대로 쌓인다**: `[사람 질문 → "질문 접수"(AI) → LLM 답변(AI) → "처리 완료"(AI)]`. 반복문으로 출력하면 흐름이 지나온 자취가 순서대로 보인다.

이처럼 노드를 늘리고 엣지로 이으면 작업 단계를 얼마든지 확장할 수 있다. 오늘까지는 갈라짐 없이 한 줄로 이어지는 **직선 그래프**다.

## 6. 더 나아가면 — 조건에 따라 갈라지는 그래프

오늘 만든 것은 START에서 END까지 한 줄로 흐르는 직선 그래프다. LangGraph의 진짜 힘은 **엣지가 상태를 보고 갈라지는 '조건부 엣지'** 에 있다. 여기서부터 반복과 분기가 가능해진다. (아래는 앞으로 배울 형태의 예시로, 흐름의 그림만 소개한다.)

**예시 1 — 모델 학습 흐름(조건 분기 + 반복).**
```
START → retrieve_data → train_model → evaluate_model →┬─(부족)→ adjust_parameters → train_model (다시 학습)
                                                       ├─(충분)→ visualize_performance → END
                                                       └─(중단)→ handle_stop_condition → END
```
`evaluate_model`에서 성능을 평가한 뒤, 결과가 **부족하면** 파라미터를 조정해 `train_model`로 **되돌아가 다시 학습**하고(반복), **충분하면** 결과를 시각화하고 끝내며, **중단 조건이면** 종료 처리로 간다. 하나의 평가 노드에서 상태에 따라 세 갈래로 갈라진다.

**예시 2 — 두 모델 병렬 + 재검색 반복(RAG).**
```
START → retrieve →┬→ GPT 요청    → GPT_relevance_check   →┐
                  └→ Claude 요청 → Claude_relevance_check →┴→ 결과 종합 →┬─(재검색)→ rewrite_query → retrieve (다시 검색)
                                                                          └─(종료)→ END
```
검색 후 **GPT와 Claude에 동시에(병렬)** 질문하고, 각 답변이 질문에 맞는지 검사한 뒤 결과를 종합한다. 종합 결과가 부실하면 **질문을 다시 써서(rewrite_query) 재검색**하는 반복으로 돌아가고, 충분하면 종료한다.

이런 **반복(루프)·분기·병렬**이 직선 파이프라인으로는 만들기 어려웠던 흐름이고, 그래서 LangGraph를 쓴다. 오늘 배운 상태·노드·엣지와 직선 그래프가 이 모든 것의 기초다.

---

## 7. 한 줄 요약

> **LangGraph**는 AI의 작업 흐름을 **그래프(순서도)** 로 그려 만드는 도구다. 세 요소만 기억하면 된다. **상태(State)** 는 모든 단계가 함께 읽고 쓰는 공유 화이트보드(`TypedDict`로 틀을 정의하고, 대화 칸은 `Annotated[list, add_messages]`로 쌓이게 한다), **노드(Node)** 는 상태를 읽어 일을 하고 결과를 상태에 적는 작업 단계(함수 하나), **엣지(Edge)** 는 노드 사이를 잇는 화살표(순서)다. `StateGraph`에 노드를 `add_node`로 등록하고 `add_edge`로 `START→…→END`를 이은 뒤 `compile()`해 `invoke`로 실행한다. 오늘은 한 줄로 흐르는 직선 그래프까지 다뤘고, 이다음은 상태를 보고 갈라지는 **조건부 엣지**로 반복·분기·병렬을 만든다.
